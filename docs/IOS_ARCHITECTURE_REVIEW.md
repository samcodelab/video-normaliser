# FrankLuma iPhone and iPad architecture review

FrankLuma can become a universal iPhone and iPad app while sharing its correction and media pipeline with macOS. Use one shared `FrankLumaCore` library and separate macOS and iOS app targets. This proposal reflects source inspection on 9 October 2026; mobile performance figures below are estimates, not device measurements.

**Evidence status:** current files, dependencies and allocation dimensions below were verified against the working tree, including the ongoing correction work. Target layout, adapter names, deployment baseline and resource policies are recommendations. No iOS target was added or compiled, and no iPhone/iPad runtime or correction-parity result is claimed. This review changes documentation only.

## Source sharing boundary

| Area | Existing source | Proposed treatment |
| --- | --- | --- |
| Correction and geometry | `Exposure.swift`, `PatchExposure.swift`, `SpatialLighting.swift`, `CommonIllumination.swift`, `PulseReconstruction.swift`, `Scenes.swift`, `VideoGeometry.swift` | Share algorithms. Keep these with the renderer initially because scene validation and spatial fitting already call it. The common-illumination and pulse-reconstruction files currently import Foundation only. |
| Media pipeline | `SpatialRenderer.swift`, `VideoEngine.swift`, `VideoExporter.swift` | Share Core Image, AVFoundation, AudioToolbox and Vision paths. Replace the apparently unnecessary AppKit import in VideoEngine. |
| Session and projects | Most of `AppModel.swift`, `ProjectDocument.swift` | Share edits, task cancellation, exact-frame timing, document schema, fingerprints and recovery logic. Extract URL-based open, save, relink and export operations from desktop dialogs. |
| Platform services | Source bookmarks, import ownership, export delivery and lifecycle | Implement separate adapters. Retain reusable SecurityScopedAccess; keep destination-volume ExportStaging behavior on macOS. |
| Interface | `FrankLumaApp.swift`, `TimelineEditor.swift` | Retain desktop UI and event handling; create adaptive SwiftUI mobile screens and touch navigation. Share timeline math and normalized region geometry. |

`Package.swift` currently declares only macOS 14 and an executable product; `Configuration/Base.xcconfig` specifies the macOS SDK. Add a Core library and platform declaration, then create an actual iOS application target for iPhone and iPad linked to it. Preserve the macOS executable workflow. Move shared tests to Core and expose only the symbols required across target boundaries.

The concrete portability blockers are AppModel's NSOpenPanel, NSSavePanel, NSAlert and export accessory view; the app's macOS window/lifecycle/player wrappers and Finder action; the timeline's NSEvent monitor; and macOS bookmark flags in ProjectDocument. These belong outside Core. An async UI can present pickers and unsaved-work decisions before calling URL-based session operations.

Foundation types with `NS` names, such as `NSLock`, `NSError`, `NSDictionary` and key-value observation, are not themselves AppKit blockers. `VideoEngine.swift` currently uses those types but no desktop view or panel API, so replacing its AppKit import with explicit shared framework imports is a small, separately compile-verifiable extraction step. Keep `TimelineViewport` math separate from its `NSViewRepresentable` event bridge. Replace the desktop `AVPlayerView` host with a SwiftUI `VideoPlayer` or a UIKit player-layer wrapper on mobile while sharing playback state and exact-frame correction.

## Apple media framework portability

AVFoundation is available on iOS, iPadOS and macOS; the current asset reader/writer and player architecture is therefore a reasonable shared implementation. Individual API availability and actual codec support still need SDK compilation and device exports. [Apple AVFoundation overview](https://developer.apple.com/av-foundation/)

Core Image kernels written in Metal are supported on both iOS and macOS. The current renderer uses Core Image's source-string `CIKernel` initializer and CIContext; there is no application-owned Metal device, command queue or `.metal` shader to port today. A future Metal kernel can share shader source and render semantics, but its library must be built for each target SDK and loaded from the correct bundle. Preserve the existing linear-sRGB working space, transforms and manual/automatic gain composition during that migration. Do not combine renderer replacement with the first Core extraction. [Apple Core Image kernel improvements](https://developer.apple.com/videos/play/wwdc2021/10159/), [Apple Metal kernel build integration](https://developer.apple.com/videos/play/wwdc2020/10021/)

## Extraction and build plan

Use logical directories inside Core initially: `Correction` for the math/scene files, `Media` for engine/renderer/exporter, and `Projects` for document coding, fingerprinting and recovery. Extract AppModel's reusable state into `EditorSession.swift`; retaining ObservableObject and AVPlayer is reasonable because both app targets use SwiftUI and AVFoundation. App-specific views should call async operations to open a source URL, restore a document with a resolved source URL, snapshot a project and export to a local URL. Move panel selection and leave-session confirmation outside those operations. Avoid separate framework targets until the existing correction-to-renderer dependency is deliberately untangled.

Proposed adapters are `SourceLocator` (bookmark creation/resolution and relinking), `ImportedMediaStore` (owned copies, stable asset IDs and cleanup), `ExportDelivery` (completed-file delivery) and `SessionLifecycle` (checkpoint/cancellation policy). macOS implementations preserve current behavior. Mobile implementations own Files/Photos transfers and SwiftUI presentation. A security-scoped URL lease must survive asynchronous processing; picker dismissal must not release the source while AVPlayer still uses it.

The iOS target needs independent build settings, Info.plist, signing/provisioning and icons; do not inherit the macOS SDK, hardened-runtime settings, desktop sandbox entitlements or framework runpath. Register the same project UTType/file extension and document opening behavior. Choose a deployment baseline explicitly; iOS/iPadOS 17 is a practical initial proposal, with newer background APIs availability-gated. Compile Core for simulator and physical-device SDKs to expose unavailable APIs and missing access control. Native Vision/GPU/encoder validation still requires hardware.

Concretely, add `Sources/FrankLumaCore` and a `.library(name: "FrankLumaCore", targets: ["FrankLumaCore"])` product; retain `Sources/FrankLuma` as the macOS executable depending on Core. Set package platforms to macOS 14 and the chosen iOS baseline. Have both Xcode application targets link that local package product, removing moved files from the existing macOS target's source-build phase so types are compiled once. Add a separate iOS app source directory outside the macOS executable target, with iPhone and iPad device families enabled. Split Core tests from desktop UI/session tests, move `@testable import` accordingly, and give application-facing Core types an intentionally small public API. Review `scripts/build-*-audit.sh`, which compile source lists directly, when files move. Adding an iOS package platform alone does not create an installable iOS application.

## Mobile resource constraints

Source inspection shows that each analyzed frame retains a 96 by 56 RGB Float thumbnail and 336 Double patches. Their payload is 67,200 bytes per frame: approximately 121 MB per minute at an assumed 30 fps, before spatial fields, array overhead, correction caches and decoded frames. Reference-region results retain additional analyses. Swift arrays can share storage, so this is a payload estimate rather than a measured peak-memory total.

The experimental `FRANKLUMA_PULSE_DETAIL` path additionally retains a 192 by 112 RGB Float thumbnail: 258,048 bytes per frame, approximately 464 MB per minute at 30 fps. It is disabled by default and needs bounded or disk-backed storage before use on long mobile clips; transient optical-flow images and retained pulse evidence have different memory costs.

These figures use decimal MB. Baseline plus retained detail is about 585 MB/minute at 30 fps and 1.17 GB/minute at 60 fps, before the other allocations; five minutes at 30 fps is already about 2.93 GB of those payloads alone. File-backed storage will require algorithm work because fitting and tracking revisit frames; writing arrays to disk alone does not bound the solver's working set. Establish a frame/window access strategy and cancellation checkpoints before claiming long-clip support.

The newer optional `meterThumbnail` adds a second 192 by 112 RGB Float image when both `FRANKLUMA_PULSE_DETAIL=1` and `FRANKLUMA_PULSE_ANALYSIS_PREFILTER=1`. This is another 258,048 bytes per frame, independently allocated from the detail image. Baseline plus both images is 583,296 bytes per frame: approximately **1.05 GB/minute at 30 fps**, 2.10 GB/minute at 60 fps, or 5.25 GB for five minutes at 30 fps, before solver, flow, preview and framework allocations. The default path does not retain either optional image. The earlier 585 MB/minute estimate applies only when detail is retained without the extra meter image.

Corrected still previews decode and render at source resolution before shrinking to 1600 by 1000; nearby previews use the same path. A 3840 by 2160 BGRA frame has approximately 33 MB of pixel payload. Limit preview caches, serialize expensive preview work, stop unnecessary playback processing, and clear dispensable caches on memory warnings. Introduce an explicit mobile worker/memory policy: the current spatial estimator selects up to six workers from processor count.

The new opt-in `FRANKLUMA_VISION_FLOW` path remains shareable. Analysis computes forward and backward Vision flow on 192 by 112 detail images, then retains 24 by 14 two-component forward/backward Float guidance. That adds about 5,376 bytes per frame, or 9.7 MB per minute at 30 fps, excluding framework working memory. Requests use revision 1 with high accuracy and are serialized by a lock, with native buffers released through autorelease pools. Apple describes optical flow requests as resource intensive and recommends one request at a time; computation generally increases with accuracy. Keep this experimental path opt-in until device quality, latency and memory tests justify enabling it. [Apple optical flow request](https://developer.apple.com/documentation/vision/vngenerateopticalflowrequest), [Apple accuracy levels](https://developer.apple.com/documentation/vision/vngenerateopticalflowrequest/computationaccuracy-swift.enum)

Current HDR rejection and the 4096-pixel dimension limit should remain initially. H.264 MP4 is the first export format; gate additional formats by writer capability and actual device exports. Preserve sample timing, final-frame holds and the existing independent audio path. The legacy force-unwrapped CIKernel source creation needs early device validation and graceful failure; a shared Metal kernel migration can follow with render comparisons. [Apple CIKernel deprecation](https://developer.apple.com/documentation/coreimage/cikernel/init%28source%3A%29), [Apple AVAssetWriter](https://developer.apple.com/documentation/avfoundation/avassetwriter)

## Import persistence and delivery

The current exporter preserves compatible original audio in MOV, preserves existing AAC in MP4, and converts other MP4 audio to AAC. Conversion uses mono/stereo output, downmixing multichannel sources to at most two channels. Preserve this behavior and audio tails in Core; test actual device decode/encode support, and describe any downmix in mobile export options. Capability checks already exist in VideoExporter but do not establish device coverage.

The newer PersistentLocalFlash, PersistentLightingSolver and PersistentSurfaceIdentity code remains inside shared SpatialLighting and introduces no desktop framework dependency. Its temporary fitting samples, basis weights and residual arrays make the earlier payload estimate a lower bound rather than a complete budget. Device measurements should include both the selected production correction path and any experimental path proposed for promotion. Replace environment-variable feature selection with explicit, reproducible engine configuration before mobile release; keep desktop and mobile defaults identical for document/render parity.

Start with Files import, retaining security-scoped access for the whole read/player lifetime. Add PhotosPicker through file-based Transferable imports into owned storage rather than loading long movies into Data. Cloud downloads need progress and cancellation. [Apple fileImporter](https://developer.apple.com/documentation/swiftui/view/fileimporter%28ispresented%3Aallowedcontenttypes%3Aoncompletion%3A%29), [Apple FileRepresentation](https://developer.apple.com/documentation/coretransferable/filerepresentation)

Project version 2 stores settings and an exact source SHA-256 fingerprint, not the movie or analysis. Keep that schema compatible, but use platform-specific source locators: desktop paths/bookmarks cannot identify a source on another device. Initially require relinking to a byte-identical original. Owned mobile imports improve reliability at the cost of disk space and need explicit cleanup. Retain imported bytes because a fresh Photos representation might differ from the fingerprint.

Render export into owned temporary storage, then deliver the completed file through Files/share sheet or an explicit Photos save. Checkpoint edits when inactive and recover after termination. Background continuation needs its own integration; current continuous background tasks require a GPU entitlement and supported-device resource checks for background GPU work. Keep a foreground fallback. [Apple long-running tasks](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados), [Apple supported resources](https://developer.apple.com/documentation/backgroundtasks/bgtaskscheduler/supportedresources)

## Phased implementation

Keep saved correction settings platform-neutral, while playback layout, preview cache size and mobile worker limits stay outside the project document. Reopening currently repeats analysis, so algorithm changes can alter results despite unchanged version-2 settings; add an engine/configuration version or documented migration policy when output stability becomes a product requirement. Optional portable source IDs or relative paths require backward-compatible decoding; incompatible schema changes need a version bump. Do not silently downgrade an unsupported saved export option: preserve it in the document and ask the mobile interface to select a supported format.

Use one universal iOS app with adaptive SwiftUI views, not two independently maintained mobile interfaces. Share controls and editor session, with a compact phone composition and regular-width iPad composition. Phone uses a persistent preview, timeline/frame stepping and one settings sheet at a time; iPad exposes scenes and inspector alongside preview when space permits. Adapt to window width rather than device name. Region selection needs sufficiently large touch targets and a zoomed precise adjustment path; frame split/join commands should remain explicit. On mobile, stop processing safely when background GPU access is unavailable, checkpoint edits and explain whether analysis/export must restart. Ordinary async tasks do not provide durable background execution.

1. Extract Core and URL-based session operations without changing correction behavior. Verify the existing macOS timing, correction and project tests.
2. Deliver the first mobile vertical slice: Files import, a short SDR clip, analysis, corrected preview and basic settings, then H.264 MP4 export/share. Test on an ordinary iPhone and an iPad. Choose initial clip/resolution limits from measured memory, runtime and thermals.
3. Add the adaptive editor and compatible saved projects/recovery/relink. Phone layout uses preview above the timeline and settings sheets; iPad uses sidebar/inspector and adapts to narrow windows. Provide pinch/drag navigation, explicit split controls and precise frame stepping.
4. Add Photos import and supported export options; introduce bounded or disk-backed analysis and caches before expanding long-clip limits. Avoid reducing frames or thumbnail fidelity without validating scene detection and surface tracking quality.

Acceptance should cover portrait transforms, variable frame rate, nonzero track starts, final frame holds, audio tails and conversion, HDR rejection, cancellation, out-of-space, cloud imports, relinking and app interruption/recovery. Source inspection establishes a feasible sharing boundary; physical-device tests must establish encoder coverage, GPU behavior, peak memory and correction parity. No mobile builds or processing measurements are implied by this review.

For each mobile milestone, record the device model, OS, source resolution/frame rate/duration and engine configuration with peak resident memory, analysis time, export time, thermal state and cancellation latency. Include the oldest supported iPhone class, a regular iPad and a faster recent device; exercise iPad narrow windows and both orientations. Compare identical source bytes and project settings with macOS: scene/frame timestamps and edit semantics should agree, while rendered pixels need a documented numerical tolerance for GPU differences. Run decoded export comparisons as well as preview comparisons, including dark/chromatic material, motion, scene cuts and brief flashes. A simulator build validates the shared API boundary; it does not establish hardware GPU, encoder or memory acceptance.

## Follow-up portability review: current pulse experiments

A second source review on 9 October 2026 confirms that the latest transported-footprint and significance experiments remain within shared math/media files. They do not require an additional iOS-specific correction algorithm. `applyPulseComposition` currently selects complete per-scene image arrays and can revisit multiple temporal intervals and fitting passes. Its transported-measurement path computes two temporary optical-flow results for each bracket. This is separate from the retained per-frame Vision guidance estimate above: include both transient peaks and retained storage in a device profile rather than adding only the retained payload figures.

Before extracting Core, introduce an explicit `EngineConfiguration` containing the selected correction feature set and a separate `ProcessingPolicy` for worker limits, preview-cache bytes and storage strategy. The configuration must be reproducible in benchmark evidence and identical across platforms; the resource policy may differ by device. Keep the experimental flags disabled until their own correction-quality acceptance succeeds. A mobile port should not silently promote or replace them. Resource limits should change scheduling/storage, rather than changing saved slider values or correction meaning.

The first extraction acceptance is deliberately small: the macOS app still opens, analyzes, previews, saves/reopens and exports the same fixture after Core is moved; pure Core tests compile for iOS; the simulator imports a short Files clip and renders the existing kernel without a crash. Physical-device exports are a separate acceptance. The deprecated source-string CIKernel is a runtime risk to test and handle, not evidence that all rendering must be rewritten before that slice. Apple's precompiled Metal initializer provides a later migration route with independent renderer-parity tests. [Apple Metal CIKernel initializer](https://developer.apple.com/documentation/coreimage/cikernel/init%28functionname%3Afrommetallibrarydata%3Aoutputpixelformat%3A%29)

The proposed iOS 17 baseline cannot use the newer continued-processing task API on every supported OS. Apple introduced that API for iOS/iPadOS 26, and background GPU availability is still a runtime capability, not an assumption based on a recent device name. Gate the implementation by OS availability and `supportedResources`, configure the entitlement where applicable, and retain interruption/cancellation/recovery behavior on the other devices. Do not describe arbitrary export as guaranteed to finish after the user leaves the app. [Apple WWDC25 background execution session](https://developer.apple.com/videos/play/wwdc2025/227/), [Apple long-running task integration](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados)

For the requested adjacent-frame adjustment workflow, use the same shared frame-selection and manual-EV state. On iPhone, let the comparison occupy the main preview with selectable neighboring frames and pinch inspection; on a wide iPad, use two or three large synchronized panels. Avoid eagerly retaining five full-resolution corrected frames. Serial, cancellable requests with a byte-bounded cache preserve inspection quality and reduce memory spikes. Rendering first and shrinking afterward currently preserves source-dependent guidance; changing to low-resolution-first rendering needs its own comparison against exports.

No additional application source, mobile target or algorithm was changed in this follow-up. The remaining uncertainties are actual device peak memory/thermals, kernel and codec behavior, interruption recovery, and numerical/rendered parity. Sharing the source is feasible; those measurements determine supported clip sizes and release readiness.

## Latest source check: optional pre-filtered analysis

The current `VideoEngine.analyse` optionally creates `meterThumbnail` from the transformed full frame using Gaussian pre-filtering followed by bicubic reduction (`B=1`, `C=0`). It uses Core Image and `CoreImage.CIFilterBuiltins`, without introducing another desktop-only dependency. Apple's typed bicubic filter exposes these same parameters; include this path in the eventual iOS SDK compilation and device comparison. [Apple bicubic scale transform](https://developer.apple.com/documentation/coreimage/cifilter-swift.class/bicubicscaletransform%28%29)

`ExposureSample` retains the optional image; the current scene reassignment and level-remeasurement paths preserve it. `applyPulseComposition` supplies it as optional photometry input only when every sample has both the necessary detail and meter images and the pre-filter flag is enabled. Registration and optical-flow geometry continue to use the original detail images. This separation belongs in shared Core: switching the measurement image only on mobile would change correction semantics. Keep the pre-filter choice in explicit engine configuration and account for its separately allocated storage in the mobile processing policy. Both flags are needed to retain the extra image, even if the pulse-composition consumer is disabled, so configuration validation should eventually reject unnecessary retention combinations.

The inspected build remains a macOS-only executable package with one macOS application target; this check does not establish an iOS build. There is no need to start with a rewritten renderer or a separate phone algorithm. The next implementation change should be a small behavior-preserving Core extraction and URL-based session boundary, followed by the short-clip Files-to-export slice described above. Add the expensive optional meter path to device acceptance only if correction-quality work promotes it. Background GPU processing still needs the supported-resource check, entitlement and cancellation/recovery integration described by Apple; the new filter does not remove those requirements. [Apple long-running task integration](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados/)

## Mobile integration details verified in the follow-up

**External-file coordination is an additional boundary.** `SecurityScopedAccess` currently manages permission lifetime, while `ProjectStore`, fingerprinting and media readers access URLs directly; there is no `NSFileCoordinator` integration in the application sources. Apple requires coordinated access when reading or writing external documents through the document picker. For the first mobile slice, prefer a coordinated import/copy into app-owned durable media storage, then run fingerprinting, analysis and playback against that stable local copy. Keep the scope alive during transfer, propagate provider/download failures, and clean up incomplete copies. A temporary Photos transfer URL must likewise be copied into owned storage before it is retained as a project source. Apple recommends `FileRepresentation` for large Photos assets to reduce memory use. Saving a project back to an external provider also belongs in the coordinated delivery adapter; destination-volume staging alone does not supply coordination. [Apple document picker requirements](https://developer.apple.com/documentation/uikit/uidocumentpickerviewcontroller), [Apple Photos picker file transfers](https://developer.apple.com/documentation/photokit/bringing-photos-picker-to-your-swiftui-app)

**Suspension must preserve recovery.** The existing `projectEdited()` debounces checkpoints by 600 ms, and `finishSession()` calls `clearCheckpoint()`. Therefore, the mobile scene-inactive/background handler must not reuse `finishSession()` or `closeSession()` as its interruption handler: that would delete the checkpoint it needs for recovery. Give the extracted session separate operations for checkpointing and suspending work, versus explicitly discarding/closing a session. Flush pending edits before suspension, pause playback, cancel disposable previews and any processing without an approved background execution path, and retain the source identity and saved settings. Existing cancellation forwarding to detached workers and generation checks are useful shared behavior, but actual cancellation latency and interrupted export cleanup still need device tests. The present reader/writer export is not a durable resumable job; label interrupted exports as requiring a restart unless a separate resume design is implemented. Apple's continued-processing API is available from iOS/iPadOS 26, with GPU access conditional on supported resources and entitlement; an iOS 17 deployment choice still needs this fallback. [Apple background task guidance](https://developer.apple.com/videos/play/wwdc2025/227/)

**Budget storage and repeated work as well as RAM.** `analyse()` decodes the movie and then hashes the entire source in 4 MiB chunks. Project reopening repeats analysis, and each distinct reference region can trigger another analysis pass and retain its own sample set. Owned mobile imports add a source copy; export adds an output file while the source remains present. Admission checks should therefore consider source bytes, expected output bytes and temporary headroom, and progress should distinguish import, analysis, fingerprinting and export. The fingerprint's chunking is already bounded; optimizing it into the import pass is a later change requiring the same exact-byte and source-change guarantees. Do not place the sole source needed for recovery in an evictable preview cache. Test out-of-space during both import and export, not only before either starts.

**Keep preview and edit semantics shared.** The current adjacent-frame implementation already requests previews sequentially, checks cancellation and rejects stale generations. Preserve these properties when building touch views; add byte-based cache limits and memory-pressure handling rather than inventing a separate mobile comparison engine. `pauseForFrameAdjustment()` freezes the selected source frame before a slider gesture; the phone and tablet controls should use that same frame identity throughout the gesture. The current `nearbyFrameImages` and cache store resized `CGImage` results, while each corrected request still renders at source resolution first. Their retained memory and their transient full-resolution memory are separate budget items.

These findings refine the existing implementation order: (1) extract Core/session without behavior changes, (2) add coordinated owned Files import and a short-clip preview/export slice, (3) add recovery-preserving lifecycle handling and adaptive touch editing, and (4) establish device memory/thermal/storage limits before expanding clip support. This follow-up inspected source and primary Apple documentation only; no processing code changed, no mobile target was created, and no iOS compilation or hardware validation is claimed.
